## Findings

1. BLOCKING. P2's stated power is wrong. Under D3's rule as written, a true 1-point loss reads harm about half the time,
   not with 0.885 to 1.000. The registration (Paths field, l.29 to 32) and STATE.md l.187 say "the least power for a true
   loss of exactly 1 point ... 0.885 (S370); every other household 7u ran 0.999 or more". That figure comes from
   reread-7u-item4.mjs l.78, `pw = normUpper(zH - 160 / Math.sqrt(nD))`, which is the McNemar condition alone. The rule
   also needs the observed loss to be at least 1 point (reduce-7uf.mjs l.89: `x.pHolm < HARM_P && x.change <= -HARM_LOSS`).
   At a true loss of exactly 1 point, the observed loss reaches 1 point only about half the time. Simulated through
   `perHousehold` itself (16,000 paths; the household against 27 in-band households with no change, so Holm runs over
   28 pairs, about 7u-F's in-band count; 400 trials each):
   ```
   S370-like (9.04% discordant): true loss 1.00 points: HARM read 0.497; 1.10: 0.670; 1.25: 0.818; 1.50: 0.983
   S224-like (2.59%):            true loss 1.00 points: HARM read 0.460; 1.10: 0.805; 1.25: 0.983; 1.50: 1.000
   low discordance (1.0%, all losses): true loss 1.00 points: HARM read 0.510
   ```
   So a PASS does not mean that no household loses 1 point. It means a loss above about 1.25 points would have been seen
   with 80% or more probability, and a loss of exactly 1 point half the time. The shortfall comes from D3's own wording,
   not from the path count: more paths do not move the 50%. This is the failure the record names (a reading of "no
   material harm" at a true loss half the time), and the registration claims the opposite on a seed that is used once.
   Fix:
   - reread-7u-item4.mjs: compute the chance that both conditions hold.
   - Reprint results-reread-7u-item4.txt and STATE.md's line.
   - The registration's Paths field: state the true loss the rule detects at 80% and at 90%.
   - Put the corrected figure to the maintainer before launch. D3 is theirs to keep knowingly or amend, and the record
     should show which.

2. MINOR. P1's power line is the 50% point and rests on 14 of the 18 floor households. "A true pooled change above about
   -0.054 reads HELD" is the change that reads HELD half the time. Reading HELD 90% of the time needs about -0.023 or
   better. The se (0.0237) leaves out S382, S406, S418 and S362. These are deposit households and are probably among the
   most discordant, so the se on 7014 is likely larger. The margin is ample all the same. On 7u's own records, 7u-F's floor
   reads +0.307 at W0.02 (by path 0.241 to 0.373, se 0.0335 at 8,000 paths) and +0.356 at W0.01 (0.290 to 0.422), most of
   it from S248 (+2.375) and S284 (+2.625). The registration should state the chance of reading HELD at a stated true
   change and name the four households its se omits.

3. MINOR. Nothing measured checks that the arms solved the same plan. In the `ran` line, `tiers` is computed from
   `candidatePlan(E, plan)`, the input (audit-7uf.mjs l.97), not from what the arm solved, so it reads the same for every
   arm whatever ran. The engine-context check (l.104 to 105) compares an arm's engine context with that arm's own solver
   context, not across arms. If SHIP had solved the raw plan, its engine and its model would agree, and every gate field
   would still match. The `ran` line also leaves out jointWorlds (checked per arm by WANT, l.88), bequestShape,
   raiseWeight, resilienceWeight, finalExact and the lattice. No fault is present: every arm is given candidatePlan (l.67;
   candidate.mjs solveCandidate), and every arm takes PRODUCT_BASELINE under its own options (solve.js solvePlan, `o =
   { ...PRODUCT_BASELINE, ...rest }`). Fix: record a hash of `ctxKey(m.ctx)` and of `m.ctx.plan.riskProfiles` in each
   unit, have gate() require them equal across a household's arms, and plant one.

4. MINOR. The audit's own checks have no planted test (CHECKLIST.md item 5). These are WANT (l.88), the estate weight
   (l.89), the lattice (l.93 to 95) and the engine context (l.104 to 105). No file in research/tests names audit-7uf.mjs.
   I showed the context check can fail. On S370, with built contexts and audit-7uf.mjs's own `ctxKey`, each of these
   reads DIFFER against the candidate's plan: guardrails on, the raw plan without O60's tiers, another floor spend,
   another solvency floor. Its blind spots are the five Map fields (oneOffContribs, oneOffCosts, oneOffDeductions,
   stagedTransfers, oneOffStaging), which serialise as `{}`. Export `ctxKey` and plant those four cases in a test.

5. MINOR. The read checks each unit's provenance only against its household's other arms.
   - The seed and path count are checked on the first unit loaded only (reduce-7uf.mjs l.140).
   - The JSON files' stamp (prediction, sha) is compared between a household's arms (l.60) but never with REGISTRATION.
   - requireFairLogs (l.132) reads the case logs, not the JSON files.
   - audit-7uf.mjs writes by default into the registered directory (l.61: `results/diag7uf`).
   So if all of one household-weight's unit files came from a manual run on another seed, they would pass. diag7uf does
   not exist now. Fix: check every unit's seed, N, `stamp.prediction === REGISTRATION` and `stamp.sha` against the logs,
   and have batch-7uf.sh refuse a diag7uf that is not empty.

6. MINOR. The adaptive reference has never been consulted in the audit. Both preflight households read 0 bridge years
   (results-preflight-7uf.txt l.14 and l.22: "the adaptive reference not consulted"). v-candidate.mjs does not print
   whether the reference was built on S370 or S380. So three things run first on 7014: the audit's adaptive branch
   (l.92 to 95), the engine executing a table that uses the reference, and the read's reference-part lines with CAND
   differing from DECOMP. A crash there leaves units missing, and a code fix then makes a mixed-code run that
   requireFairLogs refuses. One preflight unit set on S362 (O191's household, where the reference acts) on the tuning
   seed, before launch, would cover them. Its cost is about an hour of solves.

7. MINOR. A problem in DECOMP, an arm that only reports, stops the primary read. gate() refuses every figure on any DECOMP
   problem (reduce-7uf.mjs l.139). One such problem is a missing DECOMP unit. Another is CAND and DECOMP differing in
   tiersAbove: ALLOWED['CAND:DECOMP'] is readerRef alone (l.42). Yet every arm goes through the product's 'auto' rule
   (solve.js solvePlanAuto: a second solve with the tier above, kept when it is no worse on 1,000 paths of seed 7101),
   and that rule can come out differently for the two references. That is why CAND:SHIP admits tiersAbove. It is
   unlikely: in 7u, 0 of 220 units set tiersAbove. Fix: admit tiersAbove for CAND:DECOMP too, or have a DECOMP problem
   drop only the decomposition.

8. MINOR. Some things are left to judgement after the read.
   - A fidelity gap is "logged, not a result" (the registration's Primary metric). The read, though, keeps the household
     in P1 and P2 and only prints the flag (l.145 to 147 and l.163 to 164). State that the engine's figure stands.
   - The engine and runPolicy are deterministic executions of one table, and V2's bar is zero. So any discordance is a
     defect, but the flag at p below 0.05 needs at least 6 one-way paths.
   - The time box does not say what happens to 7014 if the run stops at 36 hours with units missing (resume only the
     missing units on the same snapshot and code, or the seed is spent).
   - Under P1 FALSIFIED, "the floor households that lose most" has no count.

9. MINOR. The registration's Seed field (l.24 to 26) says Phase 4's replication seed 7018 is registered and owned by
   `phase-4*.md`. check-prediction.mjs's SEED_REGISTRY and SEED_OWNERS (l.43 to 48) do not carry 7018, and `seedsIn`
   ignores any number not in the registry, so a measurement on 7018 would not be refused. 7u-F is not affected. Fix: add
   7018 and its owner to the registry, or drop the claim.
